# 아카이브 배포 통합 프롬프트

현재 대화와 첨부자료를 기준으로 **아카이브 배포를 처음부터 끝까지 수행한다.**

## 1. 기본 원칙

`아카이브 배포`는 별도의 제3 배포 방식이 아니다.

아카이브 배포는 다음을 포괄하는 상위 개념이다.

- 공개 가능한 자료 → **공개 배포**
- 개인정보·계약·법률·의료·민감 자료 → **비공개 배포**
- 하나의 프로젝트 안에 공개/비공개 자료가 섞여 있으면 양쪽 구조를 연결해서 운영

기존 프로젝트·GitHub 저장소·Vercel 프로젝트가 존재한다면 **새 저장소를 임의로 만들지 말고 기존 구조를 우선 재사용한다.**

명확하게 판단 가능한 사항은 사용자에게 다시 묻지 말고 직접 판단해서 계속 진행한다.

작업 중 문제가 발견되면 단순히 문제를 설명하고 멈추지 말고,

1. 문제 원인 판단
2. 해결 방법 선택
3. 직접 수정
4. 재배포
5. 실제 운영 URL 검증

까지 수행한다.

---

## 2. 자료 수집

현재 채팅의 내용을 단순 요약하지 말고 **하나의 기록 문서**로 재구성한다.

다음 자료를 빠짐없이 확인한다.

- 사용자 입력 내용
- 날짜
- 장소
- 인물
- 작업 내용
- 금액
- 계약 정보
- 사건/진료/농작업 등의 진행 상태
- 이미지
- 사진
- 스크린샷
- 동영상
- 음성
- 음성 녹취
- PDF
- 첨부 문서
- 외부 URL
- 관련 파일

첨부된 미디어는 가능한 한 모두 아카이브에 포함한다.

**텍스트만 배포하고 이미지·동영상·음성 등을 누락시키지 않는다.**

---

## 3. 기록 날짜와 제목

채팅 날짜와 실제 사건 날짜를 구분한다.

사용자가 특정 사건 날짜를 알려준 경우 그 날짜를 기록 기준으로 사용한다.

예:

`2026-09-23 화곡농장 더덕수확과 씨앗채취`

목록 제목과 상세페이지 제목은 반드시 **동일한 메타데이터**를 사용한다.

다음과 같은 불일치가 발생하면 안 된다.

- 목록: `2026-09-24 화곡농장 더덕수확과 씨앗채취`
- 상세: `화곡농장 더덕수확과 씨앗채취`

하나의 canonical title을 정의하고 모든 화면에서 공유한다.

권장 메타데이터:

```text
id
date
title
summary
category
visibility
tags
media
source
createdAt
updatedAt
```

---

## 4. 문서 생성

기본적으로 다음 산출물을 생성한다.

```text
README.md 또는 기록용 .md
index.html 또는 상세 HTML
관련 이미지
관련 동영상
관련 음성
관련 문서
기타 첨부파일
```

필요한 경우 ZIP도 생성한다.

ZIP 내부에서도 미디어 경로가 깨지지 않아야 한다.

---

## 5. 상세페이지 구성

상세페이지는 **실제 기록을 빠르게 확인할 수 있는 실용적인 구조**로 만든다.

불필요하게 큰 제목이나 빈 공간을 만들지 않는다.

우선순위:

1. 제목
2. 날짜
3. 핵심 요약
4. 주요 정보
5. 상세 기록
6. 사진/스크린샷
7. 동영상
8. 음성/녹취
9. 관련 문서
10. 관련 링크
11. 원본 자료

피해야 할 UI:

- 지나치게 큰 Hero 영역
- 큰 제목 때문에 생기는 넓은 여백
- 고정 높이 장식 카드
- 의미 없는 안내 카드
- `"기존 상세 이미지"` 같은 반복 문구
- `"본문 아래 첨부자료"` 같은 불필요한 안내
- 같은 설명의 반복
- 실제 정보보다 장식이 더 큰 화면

목표는 **한 화면에 최대한 많은 유용한 기록을 자연스럽게 보여주는 것**이다.

---

## 6. 목록 화면

프로젝트 홈에서는 단순 제목만 나열하지 않는다.

각 기록에 필요한 정보를 함께 표시한다.

예:

```text
날짜
제목
간단 설명
카테고리
사진 수
동영상 수
음성 수
첨부파일 수
공개/비공개 상태
```

지원할 수 있으면 다음 보기 방식을 제공한다.

- 카드형
- 컴팩트 목록형
- 날짜 중심형

정렬 기능:

- 최신순
- 오래된순
- 제목순
- 카테고리
- 필요하면 사용자 정의 순서

---

## 7. 공개 배포

공개 가능한 자료는 기존 공개 GitHub 저장소 구조를 따른다.

기본 원칙:

```text
GitHub Public Repository
        ↓
GitHub Pages
```

프로젝트마다 기존 공개 저장소가 있으면 이를 재사용한다.

공개 사이트에서 비공개 기록이 존재하는 경우 **비공개 사이트로 이동할 수 있는 링크**를 제공할 수 있다.

그러나 공개 저장소에는 다음을 넣지 않는다.

- 개인정보 원본
- 의료 원본
- 법률 관련 민감 자료
- 계약서 원본
- 비공개 사진
- 민감 음성
- 인증정보
- GitHub Token
- 비밀번호

---

## 8. 비공개 배포

비공개 자료는 기본적으로 다음 구조를 사용한다.

```text
Private GitHub Repository
        ↓
Vercel
        ↓
인증
        ↓
Private Archive
```

Private 저장소명은 기존 규칙에 따라 가능하면:

```text
<project>-private
```

형태를 사용한다.

예:

```text
mine-private
baksok-private
ungdo-private
```

이미 비공개 저장소 또는 Vercel 프로젝트가 존재한다면 새로 만들지 말고 기존 프로젝트를 사용한다.

---

## 9. 비공개 인증

비공개 아카이브 접근은 다음 중 프로젝트에 이미 적용된 방식을 우선 사용한다.

### 방법 A

Vercel Authentication

### 방법 B

별도 비밀번호 인증

프로젝트가 두 방식을 제공하도록 설계되어 있다면 사용자가 선택할 수 있도록 한다.

```text
Vercel 인증으로 열기
비밀번호로 열기
```

인증 전에는 민감한 본문이나 미디어가 노출되면 안 된다.

---

## 10. Private GitHub 데이터 구조

비공개 아카이브는 기존 프로젝트가 GitHub의 Private Repository를 원본 저장소로 사용하는 구조라면 이를 유지한다.

Vercel 배포본과 GitHub에 서로 관리되지 않는 중복 데이터를 따로 유지하지 않는다.

가능하면:

```text
Private GitHub
      ↓
Server-side GitHub API
      ↓
Vercel
```

구조를 사용한다.

GitHub에서 원본이 변경되면 사이트에서도 해당 데이터를 읽을 수 있도록 기존 구현 방식을 유지한다.

토큰은 클라이언트 코드에 노출하지 않는다.

---

## 11. 미디어 처리

아카이브 배포에서 미디어는 부가 요소가 아니라 **기록의 일부**이다.

가능한 다음 자료를 모두 포함한다.

```text
.jpg
.jpeg
.png
.webp
.gif
.mp4
.mov
.m4a
.mp3
.wav
.pdf
.txt
.doc/docx
기타 첨부파일
```

미디어 처리 시 반드시 확인한다.

- 파일 존재 여부
- 웹에서 접근 가능한지
- 경로 오류가 없는지
- 대소문자 문제
- URL 인코딩 문제
- Git LFS 필요 여부
- 브라우저에서 표시되는지
- 모바일에서 표시되는지

이미지가 깨졌다면 배포 완료로 처리하지 않는다.

---

## 12. 링크 처리

모든 링크가 같은 상세페이지로 이동하는 오류가 발생하지 않도록 한다.

각 기록마다 고유한:

```text
id
slug
URL
```

을 사용한다.

예:

```text
/view/20260923-seosan-medical-record
/view/20260923-hwagok-deodeok
/view/20260912-grass-cutting
```

목록 → 상세페이지 링크를 실제 브라우저에서 확인한다.

---

## 13. 프로젝트 홈

각 프로젝트에는 홈 화면을 둔다.

프로젝트 홈에는:

- 프로젝트 설명
- 기록 목록
- 검색
- 정렬
- 카테고리
- 공개/비공개 상태
- 최근 기록
- 관련 프로젝트

등 필요한 정보를 제공한다.

새 기록을 추가하면 프로젝트 홈도 함께 갱신한다.

---

## 14. 전체 프로젝트 인덱스

아카이브 배포 시 최상위 프로젝트 목록도 반드시 확인한다.

기준 주소:

`https://softm.github.io/projects/`

새 프로젝트 또는 새 배포가 있다면 이 인덱스에 반영한다.

각 프로젝트에 대해 가능하면 다음 정보를 표시한다.

```text
프로젝트 이름
간단 설명
공개 사이트
비공개 사이트
GitHub 저장소
최근 업데이트
```

공개 프로젝트에서 비공개 프로젝트의 존재를 안내하는 것은 가능하지만 민감한 실제 내용은 노출하지 않는다.

---

## 15. 프로젝트 간 연결

공개 사이트와 비공개 사이트가 별도 주소라 하더라도 서로 연결되는 구조를 사용한다.

예:

```text
공개 프로젝트
 ├─ 공개 기록
 └─ 비공개 기록 보기
        ↓
     인증
        ↓
   Private Vercel
```

비공개 프로젝트에서도 필요하면 공개 프로젝트로 돌아갈 수 있게 한다.

---

## 16. 배포 후 실제 검증

코드 작성이나 Git push만으로 작업 완료라고 판단하지 않는다.

반드시 실제 운영 환경을 확인한다.

검증 대상:

```text
GitHub repository
GitHub Pages
Vercel deployment
프로젝트 홈
상세페이지
최상위 projects 인덱스
이미지
동영상
음성
첨부파일
내부 링크
외부 링크
인증
모바일 화면
```

HTTP 상태도 확인한다.

특히:

```text
404
403
500
redirect loop
잘못된 slug
깨진 이미지
미디어 404
인증 우회
```

등을 검사한다.

오류가 발견되면 직접 수정 후 다시 배포한다.

---

## 17. 기존 프로젝트 전체 적용

아카이브 공통 UI 또는 구조적인 버그를 발견했다면 현재 기록만 고치지 않는다.

예:

- 목록/상세 제목 불일치
- 미디어 누락
- 모든 링크가 같은 주소로 연결
- 불필요한 반복 문구
- 과도하게 큰 상세 타이틀
- 모바일 팝업/레이아웃 문제
- Private 인증 문제

이런 문제는 **공통 템플릿 또는 공통 코드에서 수정하여 전체 아카이브에 적용**한다.

---

## 18. 작업 방식

다음과 같이 사용자에게 계속 재확인하지 않는다.

```text
이대로 할까요?
배포할까요?
다음 단계로 갈까요?
GitHub에 올릴까요?
Vercel에 올릴까요?
```

필요한 정보가 이미 있으면 그대로 계속 실행한다.

문제가 있으면:

```text
문제 발견
→ 원인 분석
→ 수정
→ 재배포
→ 검증
```

까지 수행한다.

하나의 단계가 끝났다고 작업을 멈추지 않는다.

## 19. 완료 보고

작업 완료 후 반드시 다음 정보를 제공한다.

| 항목 | 결과 |
|---|---|
| 기록 제목 | 실제 제목 |
| 기록 날짜 | YYYY-MM-DD |
| 공개/비공개 | 상태 |
| GitHub Repository | 클릭 가능한 링크 |
| 운영 사이트 | 클릭 가능한 링크 |
| 상세페이지 | 클릭 가능한 링크 |
| 미디어 | 이미지 n / 영상 n / 음성 n / 문서 n |
| 프로젝트 홈 | 반영 여부 |
| 전체 projects | 반영 여부 |
| 인증 | 정상 여부 |
| 링크 | 정상 여부 |
| 배포 상태 | 정상 / 문제 |
| 미해결 사항 | 없으면 없음 |

GitHub 저장소가 존재하지 않으면 존재하는 것처럼 말하지 말고:

```text
GitHub 저장소: 없음
```

이라고 명확히 표시한다.

## 20. 최종 완료 조건

아래 항목이 모두 충족되어야 `아카이브 배포 완료`로 판단한다.

- 내용 정리 완료
- Markdown 생성
- HTML 생성
- 필요한 미디어 포함
- GitHub 반영
- 실제 웹 배포
- 프로젝트 홈 반영
- `https://softm.github.io/projects/` 반영
- 공개/비공개 링크 연결
- 인증 확인
- 상세 URL 확인
- 미디어 로딩 확인
- 모바일 확인
- 404 확인
- 실제 운영 URL 검증

하나라도 실패하면 작업을 완료했다고 보고하지 말고 수정 작업을 계속 수행한다.

## 핵심 실행 원칙

**설명만 하지 말고 실제 결과가 정상 동작할 때까지 처리한다.**

**아카이브 배포 = 자료 정리 + 미디어 보존 + GitHub 원본 관리 + 웹 배포 + 인증 + 프로젝트 인덱스 연결 + 실제 운영 검증까지 포함한다.**


---

## 21. 프로젝트 홈·전체 프로젝트 실제 반영 강제 규칙

아카이브 기록을 새로 추가하거나 수정할 때 중앙 인덱스 반영은 선택사항이 아니라 **동일 작업의 필수 단계**이다.

반드시 다음 세 경로를 같은 작업에서 갱신하고 실제 운영 화면에서 확인한다.

1. 프로젝트의 공개 서비스/기록 홈(존재하는 경우)
2. `https://softm.github.io/projects/<project>/` 프로젝트 홈
3. `https://softm.github.io/projects/` 전체 프로젝트

`projects/projects.json` 수정, Git commit, GitHub Actions 성공만으로는 반영 완료가 아니다.

완료 판정은 실제 브라우저 렌더링 기준으로 한다.

- 프로젝트 홈에서 새 기록 카드/목록과 제목이 실제로 보여야 한다.
- 전체 프로젝트에서 해당 프로젝트 카드가 실제로 보여야 한다.
- 프로젝트 카드를 누르면 `/projects/<project>/`로 이동해야 한다.
- 프로젝트 홈에서 새 기록을 누르면 실제 운영 상세 URL로 이동해야 한다.
- Pages 배포 지연, cancelled/pending 상태, CDN/브라우저 캐시 때문에 이전 화면이 보이면 완료로 보고하지 않고 재배포 후 재검증한다.
- 저장소명과 프로젝트 홈 slug가 다른 alias를 보존한다. 예: `baksok-public` → `/projects/baksok/`.

완료 보고의 `프로젝트 홈 반영`, `전체 projects 반영`은 소스 반영 여부가 아니라 **실제 운영 화면에서 확인한 결과**를 기록한다.
